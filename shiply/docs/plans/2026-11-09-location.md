# Location Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The location module: one place that decides where an address is, for both services, with a queue so no unclear address is lost, phone memory, the place list and taught names in the database, and the sites, zones and area map every other module will use.

**Architecture:** The address engine from `address-lab` becomes the package `@shiply/address` (pure code, places passed in). The `location` module owns its own PostgreSQL schema and exposes `LocationService.resolve()` through its `index.ts`; other modules never read its tables. A manual pick publishes `location.resolved` through the platform outbox.

**Tech Stack:** as the Foundation (NestJS, Prisma `multiSchema`, Next.js, next-intl, Vitest, Playwright).

**Spec:** `shiply/docs/UI.md` (Step 3a Location app, "Notes for the Shiply app" 5 and 6, "Parcel flow" 1), `shiply/docs/TECH.md` (sections 3 and 4).

## Global Constraints

- Everything in the Foundation plan's Global Constraints still applies.
- Only the location module writes the `location` schema. Others call `LocationService` from `apps/api/src/location/index.ts`.
- Order for every address: phone memory, engine, Google Maps (only when on, under the monthly cap, and only for what the engine could not place), then the queue.
- The engine never guesses: statuses `sure` and `likely` place an address; `unsure`, `partial`, `not_found` go to the Needs location queue; `outside` is recorded as outside Greater Cairo.
- Phone memory wins over the engine only for a place a person confirmed (a manual pick, later a customer link or a delivery).
- Map chain: area → delivery zone → last mile hub → sorting facility; area → dark store for Shiply Now.
- Access: `location` view to see, use to work the queue and the finder, manage to edit places, the map, sites and zones.

## Review Focus

1. A pasted CSV with a header such as `Shipping Address1,Shipping City` is read by columns, a pasted list with commas is read line by line (the address-lab bug).
2. Two people picking an area for the same queued address at once: one wins, the other is told it was already resolved.
3. Merging two places moves their names, taught names, map links and phone memory to the kept place; nothing points at the removed one.
4. A taught or edited name takes effect on the next address without restarting the API.
5. An area mapped to a zone whose hub has no sorting facility: the map page shows the gap instead of hiding it.

### Task 3b: Google Maps as the last automatic step

**Files:**
- Create: `apps/api/src/location/geocoder/{geocoder.ts, google.geocoder.ts, fake.geocoder.ts}`
- Modify: `apps/api/src/location/location.service.ts`, `packages/db/prisma/schema.prisma` (model `GeocodeCache`), `apps/api/src/platform/settings/settings.service.ts` (two settings), `.env.example` (`GOOGLE_MAPS_API_KEY=`)
- Test: `apps/api/test/location-geocoder.test.ts`

**Interfaces:**
- Produces: `interface Geocoder { lookup(text: string): Promise<GeoAnswer | null> }`, `GeoAnswer = { lat: number; lng: number; names: string[]; precise: boolean }` (names: the result's sublocality, locality, area and governorate names in Arabic and English; precise: Google's location type is ROOFTOP or RANGE_INTERPOLATED and not a partial match).
- `GoogleGeocoder` calls the Geocoding API with `region=eg`, `language=ar` and the key from `GOOGLE_MAPS_API_KEY`; `FakeGeocoder` answers from a map given in tests.
- Model `location.GeocodeCache(normalized @id, answer Json, at)`: one paid lookup per normalized address, ever.
- Settings: `location.geocoder_enabled` (boolean, default false), `location.geocoder_monthly_cap` (integer 0 to 100000, default 5000). Count of the month's paid lookups comes from `GeocodeCache.at`.
- `resolve` order: phone memory → engine → (only when the engine says unsure, partial or not_found, the setting is on, the key is set and the cap is not reached) geocoder → queue. The geocoder's `names` are run through the engine; the result counts only if it is `sure` and `answer.precise`; it then saves `method 'geocoder'`, status `likely`, and the point. Otherwise the decision goes to the queue with the point kept as a hint.
- `AddressDecision` gains `lat Float?`, `lng Float?`, and `method` gains `geocoder`.

- [ ] **Step 1:** Tests with `FakeGeocoder`: an address the engine cannot place but the fake answers with names `['المعادي', 'القاهرة']`, precise → `method 'geocoder'`, `placeId 'maadi'`, point saved; the same address again → no second fake call (cache); fake answer not precise → queued with the point; setting off → fake never called; cap reached → fake never called, queued; a fake answer naming an unknown area → queued.
- [ ] **Step 2:** Run. Expected: FAIL.
- [ ] **Step 3:** Implement. The Google adapter has no test against the real service; its request and response shapes are checked against Google's documented format in a unit test with a recorded sample answer.
- [ ] **Step 4:** Run. Expected: PASS.
