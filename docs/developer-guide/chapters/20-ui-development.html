UI development

The web app (apps/web) is a Next.js app router project in TypeScript with Tailwind CSS. It holds no business rule of its own: every number and every decision comes from the API, and the screens only collect input, show answers and keep state in the address bar. This chapter explains how pages are built, how text and direction are handled, the brand tokens, the app frame, and every reusable building block, with the props a developer needs.

Fetching data

Server components

apps/web/src/lib/api-server.ts (marked server-only) reads the access token from the cookie and calls the API directly at API_URL with an Authorization: Bearer header and cache: 'no-store':

  • apiGet<T>(path): a 401 redirects to /login; a 404 or 403 shows the not found page (a record of another store, an old link); other errors throw.
  • apiTry<T>(path): for a secondary part of a page; answers null instead of failing, so the rest of the page still shows.
  • getMyAccess(): GET /me/access, cached once per request with React cache, so every layout and page asking gets one call. getMyProfile() returns the team member's access profile; getMerchantRights() and requireMerchantRight() serve merchant pages.

Client components

Client components (files starting with 'use client') call the API through the same origin proxy, so the httpOnly cookie is sent: apiSend(method, path, body) and apiGetClient(path) in apps/web/src/lib/api-client.ts. Both return { ok: true, data } or { ok: false, error, details? } and never throw; a network failure answers error: 'network'. After a successful change the component calls router.refresh() so the server components fetch fresh data. The accounting helper useFinanceAction() wraps this: it sends one action, shows the translated result or error message, says "sent for approval" when the answer is { status: 'pending' }, and refreshes.

The /api proxy and the middleware

The browser never calls the API host. app/api/[...path]/route.ts forwards every method to API_URL read at runtime, so one build runs on any host (described in the architecture chapter). middleware.ts runs on the Node.js runtime for the signed in areas, decides with decideAccess whether to allow, send to login, refresh the session or redirect to the person's own area, and passes the path in a request header so AppShell can show not found for a page the person may not open.

Translations, Arabic and right to left

The UI supports Arabic (right to left) and English (left to right). Strings go through translation files, never written into components.

Translations use next-intl. The locale comes from the cookie shiply_locale (en or ar, default en), not from the address, so areas keep plain paths like /finance. apps/web/src/i18n/request.ts loads messages/<locale>.json for each request. The theme is the cookie shiply_theme (system, light, dark). The language and theme menu sets the cookie with document.cookie and calls router.refresh().

Messages are one JSON file per language with top level namespaces per area: common, admin, store, merchant, rider, finance, workflow, listView, lists, documents, infoTips, apps, hr, sales, cashControl, contracts, riderPay, basata and others. Server components use getTranslations('finance.journal'); client components use useTranslations('listView'). Values take ICU placeholders: t('label', { term }). t.has(key) is used to fall back when a code may have no message (for example unknown error codes fall back to generic).

Translation keys never contain dots, because next-intl treats dots as nesting. Setting names such as sla.pick_minutes become keys like sla__pick_minutes.

A test (apps/web/src/lib/messages.test.ts) fails when Arabic and English do not have exactly the same keys, or when any key contains a dot.

Direction is set once on <html>: the root layout writes lang and dir (rtl for Arabic) from the locale. Components then use logical Tailwind classes that follow the direction (ms-, me-, ps-, start-, end-, border-s) and the rtl: variant where a picture must turn (a chevron uses rtl:rotate-180). Numbers, phones, amounts, document numbers and order numbers stay left to right inside Arabic text with the class ltr-iso:

/* Numbers, phones and order IDs stay left to right inside Arabic text. */
.ltr-iso {
  direction: ltr;
  unicode-bidi: isolate;
}

Amounts and dates always use Latin digits (the date formatters use ar-EG-u-nu-latn). Arabic text never takes letter spacing, because it breaks the joining of letters. Charts keep time running left to right in Arabic too. The brand's S arrow mark is never mirrored.

Fonts and type

Fonts are self hosted woff2 files: Plus Jakarta Sans 400 to 800 for Latin and IBM Plex Sans Arabic 400 to 700 for Arabic pages (its 700 also serves 800). Type sizes are tokens and Tailwind sizes: display 56px, h1 40px, h2 28px, h3 20px, body-lg 18px, body 16px, body-sm 14px, caption 13px, label 12px with letter spacing, and number-lg 28px for big numbers. Tables of numbers use the class tabular (tabular figures).

Contrast test

apps/web/src/styles/tokens.test.ts parses the token file and checks every text and interface pair the components use against WCAG AA in both themes: 4.5:1 for text on every ground (text, muted text, link, danger and each status color on bg, surface and surface-raised), 3:1 for form borders, focus rings and buttons against the page, plus on-primary on primary, on-accent on accent, on-status on every status color and the hero pairs. It also checks that the system dark block, the explicit dark block and .shiply-on-navy are identical, and that each app tile's icon color (white or Navy, chosen by tileInk) is readable on the tile.

Layout: apps, top bar and menus

Team members land on /home, a screen of app tiles. The tiles come from appsFor(profile): an app shows when the person has at least view on its access app (Settings needs manage) and at least one page they may open. A person with store use also gets the Store screens tile.

Inside an app, AppShell (a server component) draws the AppBar and the page. It reads the profile, the theme and the path header; when the path is a page on a menu the person may not open, it answers not found. AppBar holds the grid button back to /home, the app's name, its menus and the account menu. A menu with one page is a plain link; a menu with several opens a list. Counts (badges) show next to a page and its menu. On phones (below the lg breakpoint) the menus fold into one Menu button that lists them all.

Every app, menu and page is defined once in apps/web/src/lib/apps.ts. Pages keep their addresses; the file only says which app and menu each belongs to and what access it needs:

The Accounting menus are organised by job: Dashboard, Money in, Money out, Cash and bank, Reports, Planning, Month end and Setup. locate(pathname) finds the page with the longest matching address, so a document such as /finance/bills/<id> lights the Bills menu. canOpenPage applies the page's need with canDo from packages/shared, the same function the API uses. A test (apps/web/src/lib/apps.test.ts) checks which apps and pages each job role sees.

The account menu (AccountMenu) is one Settings button on every signed in screen. It opens Help (the standard operating procedure of the person's role), Notifications, Tickets (team members and riders only), language, theme and Sign out, so these never take a row of a phone screen. It shows the person's photo from My HR when there is one.

Grid cells never grow wider than their column (.grid > * { min-width: 0 } in globals.css), so a wide table scrolls inside its own box and pages never slide sideways on a phone.

State in the address

The list's whole state lives in the address, so Back works and a view can be shared as a link. The parameters, read and written by parseListState and serializeListState in packages/shared/src/list-view.ts:

Search, filters, grouping and favourites

The search bar shows one chip per active facet: the typed search, one chip per filter group (its filters joined by "or"), the value filters and the grouping. Backspace in an empty search box removes the last chip. The Filters panel lists the predefined filters by group and the value filters: pick lists apply at once, days apply with an Apply days button. The Group by panel toggles up to two levels; a grouped list first shows the groups with counts and subtotals, and opening a group fetches its rows with open=<keys joined by a newline>.

Favourites save the current view under a name, per person and per list (user_list_favorites, routes GET/POST/DELETE /me/list-favorites, audited list.favorite_save). One favourite can be the default: it opens when the address names no list state. The column chooser saves the visible columns per person (PUT /me/list-prefs/:list) and caches them in localStorage (shiply-cols:<listId>), wrapped in try and catch because storage may be off.

Selection and bulk actions

Ticking rows shows a sticky bulk bar with the list's actions. A bulk action is declarative:

export interface BulkAction {
  key: string;
  label: string;
  endpoint: string;               // POSTed with { ids, note?, ...body }
  body?: Record<string, unknown>;
  note?: 'required' | 'optional'; // a reason asked before it runs
  tone?: 'primary' | 'danger';
  choice?: { field: string; label: string; options: { value: string; label: string }[] };
}

The endpoint answers { results: [{ id, ok, error }] }. On the API, eachRecord (apps/api/src/common/bulk.ts) runs the single record action for each id in its own transaction, so each record still goes through every rule (never one's own, the approval limit, scope) and one refusal never stops the others. The bar then shows how many succeeded and why the others were refused, in the reader's language (listView.errors).

Exports, totals and paging

Export CSV and Export Excel fetch every row that passes the current state (all=1, up to LIST_MAX_ROWS, 5,000), keep only the ticked rows when some are ticked, and build the file in the browser with exportCsv or exportXlsx from packages/shared/src/export-file.ts:

  • CSV starts with a UTF-8 byte order mark so Excel shows Arabic, uses Windows line ends, and prefixes cells starting with =, +, - or @ with a quote (unless they are plain numbers) so a spreadsheet never runs them as formulas;
  • Excel is a minimal .xlsx written by hand: one sheet, inline strings and numbers, stored in a zip with its own CRC32, no library; an Arabic export sets the sheet right to left;
  • money columns are written as EGP numbers with two decimals, dates as YYYY-MM-DD, statuses in the reader's words.

Totals of the summed columns cover every row that passed the filters, not only the page. Paging shows the counts and the page size choice. On phones (below md) rows become cards with the primary column as title.

Chatter

The chatter sits beside the content. It has four parts:

  • Notes: append only (trigger on record_notes), audited record.note. Routes GET/POST /records/:entityType/:entityId/notes.
  • Activities ("Remind me"): a Cairo day, a note and a person who may open the record (GET /records/:entityType/:entityId/people lists them). Done by that person or whoever planned it (POST /records/activities/:id/done). A web push activity_due is sent once on its day, and the person's activities are listed on the Accounting dashboard (GET /me/activities).
  • Attachments: receipt photos and other photos of the record, each labelled with what it shows.
  • History: the audit rows of the record (RecordHistory, from GET /history/:entityType/:entityId).

Reading needs view on the record's app (RECORD_APPS) and the record inside the person's stores and merchants; writing needs use. Customer records also need the customer data switch.

DateInput, Amount and money parsing

DateInput

DateInput (components/DateInput.tsx) is a text box that always reads day first (dd/mm/yyyy), as in Egypt, whatever language the browser runs in (the browser's own date box follows the device and may show month first). The form still receives YYYY-MM-DD under name, and a calendar button opens the device's own picker. Props: name, value or defaultValue, onChange (receives { target: { value } } like an input), max, className. An unreadable date marks the box invalid. The conversions are isoToDayFirst and dayFirstToIso in lib/day-first.ts, which refuse days that do not exist.

Amount and formatting

/** An EGP amount, kept left to right in Arabic, red when negative. */
export function Amount({ piastres, strong = false }: { piastres: number; strong?: boolean }) {
  const value = piastres === 0 ? 0 : piastres;   // -0 shows as 0.00, never "-0.00"
  return (
    <span className={`ltr-iso ${strong ? 'font-bold' : ''} ${value < 0 ? 'text-danger' : ''}`}>
      {formatEgp(value)}
    </span>
  );
}

formatEgp (lib/format.ts) shows piastres as EGP with two decimals and Latin digits. Other formatters show Cairo times and dates (formatCairoTime, formatCairoDateTime, formatCutoffDay).

Parsing typed amounts without floats

/** EGP typed by a person ("1,249.50", "-20") to integer piastres without going through a float. */
export function parseEgp(text: string, { allowNegative = false } = {}): number | null {
  const clean = text.trim().replace(/,/g, '');
  const match = /^(-)?(\d+)(?:\.(\d{1,2}))?$/.exec(clean);
  if (!match || (match[1] && !allowNegative)) return null;
  const value = Number(match[2]) * 100 + Number((match[3] ?? '').padEnd(2, '0'));
  return match[1] ? 0 - value : value;
}

The integer part and the decimals are read separately, so "0.29" is 29 piastres exactly, where a float would give 28.999. Contract price imports on the API use the same idea (egpTextToPiastres in packages/shared/src/contracts.ts).

StatCard, WalletCard and charts

StatCard (components/StatCard.tsx) is the dashboard number card after the brand guide's product screen: a soft rounded card, the icon on top in the status color (or a short color mark without an icon), the large tabular number, then the label. Props: label, value (already formatted), hint, tone (primary, new, in-progress, heading-to-customer, delivered, needs-action, returning), icon, and alert (the number takes the needs action color).

WalletCard (components/WalletCard.tsx) is the money balance card after the guide's cash on delivery balance card: a Navy ground (Shiply Blue in the dark theme), a small spaced label, the amount large in Cream, the note in Lime and the S arrow mark faint in a corner. Props: label, value, hint, icon, large. It is used for wallets and balances only.

Charts are drawn in HTML and SVG without a chart library, one series in the primary color:

InfoTip and the Accounting search

InfoTip explains an accountant's word in plain language: a small "i" next to a title that opens a tooltip on hover, focus or tap. Its prop term is one of journal, trialBalance, receivables, accrual, withholding, balanceSheet, cashFlow; the words live under infoTips in the messages.

AccountingSearch is the one search box in the Accounting top bar (GET /finance/search). Printing and PDF generation

Two ways produce paper:

  • Browser print for invoices, payslips, statements and comparative statements: PrintButton calls window.print(), the person saves as PDF from the print window. Menus, buttons and the chatter carry print:hidden, the main area drops its width limit, and @media print in globals.css prints black on white.
  • Server PDF with pdfkit for documents that must look the same everywhere: the drill reports (GET /finance/reports/:report/export.pdf?lang=en|ar, report-pdf.ts), the aging reports (aging-pdf.ts) and the merchant contract.

pdfkit shapes Arabic letters through fontkit, but it lays a line out as one left to right run. PdfWriter in apps/api/src/common/pdf.ts therefore lays words out itself: each word is measured and drawn on its own, in visual order. Words with Arabic letters read right to left inside their run, numbers and Latin words left to right, and an Arabic page places the runs from the right. Brackets are mirrored inside Arabic runs, and lines wrap by words. The fonts are the brand fonts (apps/api/assets/fonts).

/** A line's words in the order they are drawn from left to right. */
export function visualWords(text: string, rtl: boolean): { word: string; arabic: boolean }[] {
  const words = text.split(/\s+/).filter(Boolean);
  const runs: { arabic: boolean; words: string[] }[] = [];
  for (const word of words) {
    const arabic = LETTER_OR_DIGIT.test(word) ? ARABIC.test(word) : (runs[runs.length - 1]?.arabic ?? rtl);
    const last = runs[runs.length - 1];
    if (last && last.arabic === arabic) last.words.push(word);
    else runs.push({ arabic, words: [word] });
  }
  const ordered = rtl ? [...runs].reverse() : runs;
  return ordered.flatMap((r) => (r.arabic ? [...r.words].reverse() : r.words).map((word) => ({ word, arabic: r.arabic })));
}

Push notifications

The app is an installable web app with web push for every role. The parts:

  • Browser: PushRegistrar (in the root layout, production builds with push keys only) registers /sw.js and, for a signed in person who already allowed notifications, sends the device's subscription and language to POST /me/push/subscriptions again when it changed. The /notifications page (PushSettings) asks for permission and lets the person switch each type on or off. On an iPhone it needs Add to Home Screen.
  • Server: devices are stored in push_subscriptions (deleted when the push service answers 404 or 410), choices in notification_preferences (on by default). dispatchPush (packages/db/src/push.ts) runs every 10 seconds from the API jobs, reads the last 15 minutes of events, and notifies only people who may open the linked page, in the device's language. Each event key is claimed once in push_sent, so overlaps send nothing twice. Sending sits behind the PushSender boundary (HttpPush with the VAPID keys; FakePush in tests); without keys nothing is sent.

Types that concern accounting: finance_approval (a request or withdrawal waiting), cash_difference, rider_cash_overdue, rider_wallet (approved, paid or rejected withdrawal), merchant_payout, activity_due (a chatter reminder), payslip_ready, expense_claim, basata_deposit, rider_frozen. The texts in both languages live in packages/shared/src/push.ts, and pushTypesFor decides which types a person can receive from what they may open.
