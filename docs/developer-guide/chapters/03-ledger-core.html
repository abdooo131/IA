The ledger core

All money in Shiply Now lives in one double entry ledger. Every money event, from a rider collecting cash at a door to the year end close, is one ledger entry made of two or more lines whose amounts add up to zero. Balances are never stored; they are always summed from the lines. This chapter describes the tables, the one function that writes to them, the database rules that guard them, how balances are read and checked, and how periods are closed.

Money is a double entry ledger in piastres. Every entry's lines add up to zero (a deferred database trigger refuses anything else) and ledger rows are append only; corrections are new entries. Balances are always summed from lines, never stored. Debit is positive.

Tables

Three tables hold the ledger. They are defined in packages/db/prisma/schema.prisma (models LedgerAccount, LedgerEntry, LedgerLine) and created by the migration 20261027090000_finance, with columns added by later migrations (profit dimensions, cost tags, foreign currency).

ledger_lines

One side of an entry. Debit is positive, credit is negative, in piastres. A line of zero is refused by a CHECK constraint (ledger_lines_amount_not_zero).

ColumnMeaning

Indexes exist on (account_id, occurred_at) and on each tag with occurred_at, because nearly every report sums lines of an account, or of a tag, over a period.

post(): the only way to write

Every domain function that moves money calls post in packages/db/src/finance/ledger.ts. Nothing else inserts into the ledger tables. Its input:

export interface PostInput {
  kind: string;
  idempotencyKey: string;
  occurredAt?: Date;
  memo?: string;
  orderId?: string | null;
  data?: Prisma.InputJsonValue;
  createdById?: string | null;
  /** Where the whole entry counts; worked out from the order and wallets when left out. */
  darkStoreId?: string | null;
  merchantId?: string | null;
  riderId?: string | null;
  /** Debit positive, credit negative. Lines of zero are dropped. A line's own tags win. */
  lines: { account: AccountRef; amount: number; tags?: LineTags; foreign?: ForeignAmount }[];
}

An account is named by an AccountRef: by kind for wallets and system accounts ({ type: 'merchant', merchantId }, { type: 'vat_payable' }) or by id for any account ({ id }). Accounts named by kind are created the first time they are used (see the chart of accounts chapter).

Step by step

  1. Drop zero lines and check integers. Lines of zero are removed. Any amount that is not a safe integer is refused with amount_not_integer. If no line is left, post returns null and writes nothing. This is why a fee of 0 under a contract books nothing.
  2. Check the balance in code. The sum of the lines must be zero and there must be at least two lines; otherwise post throws a plain Error (a programming mistake, not a business refusal), which answers 500.
  3. Open a transaction (or join the caller's) with inTransaction.
  4. Idempotency. If an entry with the same idempotency_key exists, return it and write nothing.
  5. Books lock. assertPeriodOpen(tx, occurredAt) refuses a moment before books_lock.locked_before with books_closed.
  6. Line extras. checkLineExtras: a line on a bank account in another currency must carry its foreign amount (foreign_currency_account otherwise), an EGP account never carries one, foreign cents must be integers, and every cost tag named must exist.
  7. Serial number. nextNumber(tx, 'ledger_entries') takes a transaction level advisory lock on hashtext('number:ledger_entries') and returns MAX(number) + 1. The lock is held until the transaction ends, so two postings cannot take the same number and no number is skipped.
  8. Insert the entry.
  9. Resolve accounts. Each AccountRef becomes an account id, creating the account when a wallet or system account is used for the first time.
  10. Work out the tags with entryTags (below).
  11. Insert the lines, each with its tags (a line's own tags win over the entry's), cost tag and foreign amount.
  12. Commit. At commit the deferred trigger checks again that the entry balances.
export async function post(db: Db, input: PostInput) {
  const lines = input.lines.filter((l) => l.amount !== 0);
  for (const l of lines)
    if (!Number.isSafeInteger(l.amount)) throw new DomainError('amount_not_integer', 400);
  if (lines.length === 0) return null;
  const total = lines.reduce((s, l) => s + l.amount, 0);
  if (total !== 0 || lines.length < 2) throw new Error(`unbalanced ledger entry ${input.kind}`);

  return inTransaction(db, async (tx) => {
    const seen = await tx.ledgerEntry.findUnique({ where: { idempotencyKey: input.idempotencyKey } });
    if (seen) return seen;
    const occurredAt = input.occurredAt ?? new Date();
    await assertPeriodOpen(tx, occurredAt);
    await checkLineExtras(tx, lines);
    const entry = await tx.ledgerEntry.create({
      data: { number: await nextNumber(tx, 'ledger_entries'), kind: input.kind, ... },
    });
    ...
  });
}
Because nextNumber serialises every posting on one advisory lock, two postings never run their number step at the same time. For a pilot volume this is the price of gapless numbers. A system with much higher volume could number entries at the end of the day instead.

Tag inference order

Every line carries a store, merchant and rider tag when one can be found, so reports can split income and costs without extra bookkeeping. entryTags fills each tag in this order, stopping at the first value found:

  1. what the caller passed on the entry (darkStoreId, merchantId, riderId);
  2. the order of the entry (orders.dark_store_id and orders.merchant_id);
  3. the owners of the wallets on the entry's lines (a merchant wallet gives the merchant, a rider wallet the rider, a store box the store);
  4. for the store only: the rider's own store.

A tag given on a single line (lines[i].tags) wins over the entry's tag for that line. The user_id and cost_tag_id of a line come only from the line's own tags. Lines with no store are company wide.

Postings started by a person (an expense, a transfer, a journal entry) use the client generated idempotency key of the request, with a prefix: expense:<key>, transfer:<key>, journal:<key>. A form in the web app creates its key with newActionKey() (apps/web/src/lib/ids.ts, a random UUID with a fallback for plain http) and keeps it until the action succeeds, so a double click or a retry after a lost answer posts once.

Worked example: a delivered order

A merchant's contract charges an order fee of 15.00 EGP fixed plus 2% of the products value, no COD fee, no shipping fee. VAT is 14% (fee.vat_bp = 1400). Rider pay is 20.00 EGP per delivered order. A rider delivers an order whose products are worth 500.00 EGP and collects 550.00 EGP in cash. postDeliveryCompleted runs inside the delivery transaction and posts:

Entry kindAccountDebitCredit
cod_collected1300 rider cash (rider's wallet)550.00
cod_collected2100 merchant (merchant's wallet)550.00
order_fee2100 merchant28.50
order_fee4101 delivery and service fees25.00
order_fee2301 VAT payable3.50
rider_bonus5101 rider pay per delivered order20.00
rider_bonus2200 rider bonus (rider's wallet)20.00

The order fee is 1500 + share(50000, 200) = 1500 + 1000 = 2500 piastres and its VAT is share(2500, 1400) = 350 piastres. The COD fee, shipping fee, per product prices and packaging charge are 0 here, so their posts write nothing. Every line is tagged with the order's store and merchant; the lines of the two entries that touch a rider wallet (cod_collected and rider_bonus) are also tagged with the rider, because the tags are worked out per entry. Afterwards the merchant's wallet holds a credit of 521.50 EGP: the company owes the merchant the cash collected minus the fee and its VAT.

The fee lines come from one helper, so every fee kind charges VAT the same way:

async function feeLines(tx: Tx, merchantId: string, fee: number) {
  const vat = share(fee, await getSetting(tx, 'fee.vat_bp'));
  const merchant: AccountRef = { type: 'merchant', merchantId };
  return [
    { account: merchant, amount: fee + vat },
    { account: { type: 'revenue' } as AccountRef, amount: -fee },
    { account: { type: 'vat_payable' } as AccountRef, amount: -vat },
  ];
}

Database guards

The code checks every rule first so it can answer with a clear code, but the database enforces the hard rules too, whatever the caller.

Append only

-- Ledger rows are history: never changed or removed (corrections are new entries).
CREATE TRIGGER "ledger_entries_append_only" BEFORE UPDATE OR DELETE ON "ledger_entries"
  FOR EACH ROW EXECUTE FUNCTION "reject_append_only_change"();
CREATE TRIGGER "ledger_lines_append_only" BEFORE UPDATE OR DELETE ON "ledger_lines"
  FOR EACH ROW EXECUTE FUNCTION "reject_append_only_change"();

reject_append_only_change() (from the first migration) raises an error with restrict_violation. The same function guards stock_movements, order_events, audit_log, ticket messages, order notes, record notes and packaging movements. A mistake in the books is corrected by a new entry that turns the old one round (a reversal) or by an adjustment with a written reason.

Every entry balances

CREATE FUNCTION "ledger_entry_must_balance"() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE total BIGINT; lines INT;
BEGIN
  SELECT COALESCE(SUM("amount_piastres"), 0), COUNT(*) INTO total, lines
    FROM "ledger_lines" WHERE "entry_id" = NEW."entry_id";
  IF total <> 0 OR lines < 2 THEN
    RAISE EXCEPTION 'ledger entry % does not balance (total %, % lines)', NEW."entry_id", total, lines;
  END IF;
  RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER "ledger_lines_balance" AFTER INSERT ON "ledger_lines"
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION "ledger_entry_must_balance"();

The trigger is deferred to commit time, so post can insert the lines one by one; at commit each entry touched must add up to zero with at least two lines, or the whole transaction fails.

Closed periods

CREATE FUNCTION "ledger_line_period_open"() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE lock_at TIMESTAMP(3);
BEGIN
  SELECT "locked_before" INTO lock_at FROM "books_lock" WHERE "id" = 'books';
  IF lock_at IS NOT NULL AND NEW."occurred_at" < lock_at THEN
    RAISE EXCEPTION 'books_closed: % is inside a closed period', NEW."occurred_at";
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER "ledger_lines_period_open" BEFORE INSERT ON "ledger_lines"
  FOR EACH ROW EXECUTE FUNCTION "ledger_line_period_open"();

Other money tables carry CHECK constraints too (for example a cash handover's difference must equal expected minus counted, and a payout's amount must be positive). Tax invoices and frozen contract versions are protected by their own triggers.

Balances

No balance column exists anywhere. A balance is the sum of an account's lines, optionally before a moment:

/** Debit minus credit of one account, optionally up to (not including) a moment. */
export async function balanceOf(db: Db, ref: AccountRef, before?: Date): Promise<number> {
  const result = await db.ledgerLine.aggregate({
    where: {
      account: 'id' in ref ? { id: ref.id } : { key: accountKey(ref) },
      occurredAt: before ? { lt: before } : undefined,
    },
    _sum: { amountPiastres: true },
  });
  return result._sum.amountPiastres ?? 0;
}

balancesByType sums many accounts in one grouped query. Reports such as the trial balance sum debits and credits per account over a period with one SQL query (sumsByAccount in books.ts), optionally filtered by the store or merchant tag and optionally leaving out the year_close entry.

Sign convention

Raw balances are debit minus credit. Assets and expenses normally have a debit (positive) balance; liabilities, equity and income normally have a credit (negative) balance. Screens and reports show every balance as an accountant reads it, positive on its normal side:

/** Debit balances are normal for assets and expenses; the rest are shown with the sign flipped. */
export function debitNormal(category: AccountCategoryName) {
  return category === 'asset' || category === 'expense';
}

/** The balance as an accountant reads it: assets and expenses debit, the rest credit. */
export const natural = (category, raw: number) => (debitNormal(category) ? raw : 0 - raw);

So what we owe a merchant (a credit on their 2100 wallet) is shown as a positive amount owed: merchantOwed returns the balance with its sign flipped. When a merchant's wallet turns to a debit balance (fees and charges passed the cash collected), the merchant owes us; the receivables and aging screens list those merchants.

Holding money: lockedBalance and mustHold

Money cannot leave a bank or cash box that does not hold it: neither at the movement's own moment (a past day for a backdated movement) nor at any later moment up to now.

Two payments from the same box at the same time must not both spend the same money. Every check that a bank or box holds an amount takes a row lock on the account first, inside the transaction that posts the payment:

export async function lockedBalance(tx: Tx, ref: AccountRef) {
  const found = 'id' in ref ? { id: ref.id }
    : await tx.ledgerAccount.findUnique({ where: { key: accountKey(ref) }, select: { id: true } });
  if (!found) return { accountId: null, balance: 0 };
  await tx.$queryRaw`SELECT id FROM ledger_accounts WHERE id = ${found.id} FOR UPDATE`;
  return { accountId: found.id, balance: await balanceOf(tx, { id: found.id }) };
}

openAccount in books.ts takes the same FOR UPDATE lock and checks that the account belongs to the expected groups and is open. mustHold then checks the amount against the running balance, which matters for backdated movements: paying 1,000 EGP dated last Tuesday must not make last Wednesday's balance negative, even if the box holds enough today.

export async function mustHold(tx: Tx, account: Pick<LedgerAccount, 'id'>, amount: number, at = new Date()) {
  await assertPeriodOpen(tx, at);
  const rows = await tx.$queryRaw`
    WITH moments AS (
      SELECT occurred_at, SUM(amount_piastres)::bigint AS amount FROM ledger_lines
      WHERE account_id = ${account.id} GROUP BY occurred_at
    ), running AS (
      SELECT occurred_at, (SUM(amount) OVER (ORDER BY occurred_at))::bigint AS balance FROM moments
    )
    SELECT
      (SELECT balance FROM running WHERE occurred_at <= ${at} ORDER BY occurred_at DESC LIMIT 1) AS at_balance,
      (SELECT MIN(balance) FROM running WHERE occurred_at > ${at}) AS later_min`;
  const atBalance = Number(rows[0]?.at_balance ?? 0);
  const laterMin = rows[0]?.later_min == null ? atBalance : Number(rows[0].later_min);
  if (amount > Math.min(atBalance, laterMin)) throw new DomainError('not_enough_money');
}

Lines at the same moment count together. The check refuses with not_enough_money. A day inside closed books answers books_closed first, whatever the balance.

Cairo days and months

A movement entered for a past day is booked at noon Cairo time of that day; one entered for today is booked now. A future day is refused:

/** When a money event happened: a past Cairo day at noon, or now for today and no day. */
export function eventTime(day: string | undefined, now: Date = new Date()) {
  if (!day || day === cairoDay(now)) return now;
  if (!isCalendarDay(day)) throw new DomainError('invalid_date', 400);
  if (day > cairoDay(now)) throw new DomainError('future_date', 400);
  return new Date(cairoDayStart(day).getTime() + 12 * 3600_000);
}

A period of Cairo days [from, to] is turned into instants as cairoDayStart(from) (included) to cairoDayStart(addDays(to, 1)) (excluded). In SQL, grouping by Cairo day or month always converts from UTC first, because occurred_at is stored without a time zone:

SELECT to_char((l.occurred_at AT TIME ZONE 'UTC') AT TIME ZONE 'Africa/Cairo', 'YYYY-MM') AS month, ...

Writing only AT TIME ZONE 'Africa/Cairo' on a value without a time zone would read it as Cairo time and shift it the wrong way; the double conversion was made a rule after a review found this mistake.

Closing the books

The table books_lock has a single row (id = 'books', enforced by a CHECK) holding closed_through (a Cairo day) and locked_before (the instant the next Cairo day starts). Nothing may be posted before locked_before: assertPeriodOpen answers books_closed and the database trigger refuses it as well.

closeBooks in controls.ts:

  • accepts only a day already over in Cairo (day_not_over otherwise);
  • takes the advisory lock books_lock so two people cannot move it at once;
  • moving the date forward closes more days; moving it back reopens days and needs an admin (in the API: a person with settings manage) and a reason of at least five characters (reopen_admin_only, reason_required);
  • writes an audit row finance.books_close or finance.books_reopen with the old and new day.

Jobs respect the lock: a storage day, a depreciation month or a recurring month that falls inside closed books is skipped or charged on the first open day, as each job's rules say.

Closing a year

closeYear in period.ts moves the year's profit into retained earnings:

  1. Only a year already over can be closed (year_not_over), each year once (year_already_closed, the entry key is year_close:<year>) and in order (earlier_year_open when income or expense accounts still carry balances from before 1 January of that year).
  2. Under the books_lock advisory lock, it sums every income and expense account up to the end of the year.
  3. The closing entry is dated one millisecond before the new year (in Cairo time). If the books are locked past that moment, the lock is moved just before it for this one entry, in the same transaction.
  4. It posts one year_close entry: each income and expense balance turned round to zero, and the total against 3401 retained earnings.
  5. It sets the books lock through 31 December (or keeps a later lock), and writes the audit row finance.year_close.

Profit and loss reports leave the year_close entry out, so a closed year still shows its income and costs. The balance sheet shows the profit of the current year (not yet closed) as its own line next to equity, so assets always equal liabilities plus equity plus earnings.
