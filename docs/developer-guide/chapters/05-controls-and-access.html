Controls and access

The ledger guarantees that the books always balance. The controls in this chapter guarantee that the right people move money, that large or sensitive movements are seen by a second person, that closed periods stay closed, and that every change can be traced. They are implemented in packages/shared/src/access.ts, apps/api/src/auth, packages/db/src/finance/controls.ts and packages/db/src/audit.ts.

Access profiles

Team members (roles admin, finance, store_staff) each have one access profile, stored in user_access (one row per user) and user_stores (the stores of a person limited to some stores). A profile holds:

  • a level per app: store, operations, inventory, merchants, customers, accounting, hr, sales, settings. Levels are none < view < use < manage. The store screens have no view level and settings has only none and manage;
  • all_stores: every store, or only the listed ones;
  • switches: customer_data (named customer profiles), salaries (salaries, payslips, payroll), own_merchants_only (account managers see only their merchants), own_deals_only (sales reps see only their deals);
  • job_role: the template the profile was last filled from, or custom.

Job roles are templates in JOB_ROLE_TEMPLATES. The ones that matter for accounting:

How a route is protected

The AccessGuard (apps/api/src/auth/access.guard.ts) runs on every request after the JWT guard. For a route with an @Access rule:

  1. A rider or merchant passes only where the route's @Roles names them; otherwise 403 { error: 'forbidden' }.
  2. For a team member it loads the access profile fresh from the database, once per request (loadAccess), so a change made by an admin applies at once without signing in again.
  3. The needed level is the rule's level, or view for GET and HEAD and use for the rest. The person must reach it in one of the rule's apps, and every level listed in also; otherwise 403 { error: 'no_access' }.
  4. customerData and salaries in the rule need the switches.
  5. Any store id the request names (:storeId, the rule's storeParam, ?darkStoreId) must be one of the person's stores (store_not_allowed), and any merchant id must be one of theirs when they are limited (merchant_not_allowed).
  6. For merchant users, @MerchantRight checks the member's rights.

Lists and reports go further than the guard: a person limited to some stores sees only rows of their stores. List loaders receive a ListScope ({ userId, storeIds, merchantIds }, null meaning all) built by scopeOf(user, access); single records outside the scope answer store_not_allowed. The cash position and the dashboard show such a person only their boxes, riders and handovers.

The web app applies the same rules to decide what to show: each page in apps/web/src/lib/apps.ts names the level it needs, menus hide pages a person may not open, and opening one directly shows not found. The API remains the authority.

The second person rule

Money said to come in, and changes to what we owe a merchant, wait for a second person while finance.approve_money_in is 1. Money going out waits for a second person from finance.approval_threshold_piastres. Nobody approves their own request or payout.

The reason is simple: if one person could record money coming in on paper and then pay it out as a payout or an expense, money could be created and taken. So every claimed money in is checked by someone else, and every large payment too.

SettingDefaultMeaning
finance.approve_money_in1Owner capital, other income, merchant payments to us, merchant balance changes, cheques received, deposits received, loans received, asset disposals and debit notes wait for a second person (1) or post at once (0).
finance.approval_threshold_piastres1,000,000 (10,000 EGP)Payouts, expenses, drawings and other money going out from this amount need a second person; 0 turns it off.

Post now or wait

Every money screen calls a submit... function instead of the posting function directly. submit in controls.ts decides:

const reviewed =
  payload.kind === 'credit_note' ||
  (alwaysReviewed(payload)
    ? (await getSetting(db, 'finance.approve_money_in')) === 1
    : await needsApproval(db, amount));
if (!reviewed) {
  const entry = await execute(db, payload, actorUserId);
  if (receiptPhotoId) await attachReceipt(db, { entryId: entry.id, photoId: receiptPhotoId, actorUserId });
  return { status: 'posted' as const, entry };
}
return { status: 'pending' as const, request: await queueRequest(db, payload, actorUserId, receiptPhotoId) };

The answer tells the screen what happened: { status: 'posted', entry } or { status: 'pending', request }. The web helper useFinanceAction shows "sent for approval" for a pending answer.

 money in (capital, other income, merchant receipt, adjustment, cheque in,
           deposit in, loan in, disposal, debit note)
   └─ finance.approve_money_in = 1 ──▶ request: pending
   └─ finance.approve_money_in = 0 ──▶ posted at once

 credit note ─────────────────────────▶ request: pending (always)

 money out (expense, drawings, bill payment, tax payment, prepayment, asset,
            packaging, advance, bonus, payroll, petty cash, cheque out,
            deposit out, loan payment)
   └─ amount < limit (or limit 0) ───▶ posted at once
   └─ amount ≥ limit ────────────────▶ request: pending

 request: pending ──approve (another person, accounting manage)──▶ approved ──▶ posted
                  ──reject (another person, with a note)─────────▶ rejected
                  ──cancel (the person who asked)────────────────▶ cancelled

Journal entries follow the same rule through submitJournalEntry: an entry that touches no bank or cash box posts at once; one that brings money into a bank or box waits while finance.approve_money_in is 1; one that takes money out waits from the limit. All checks of the entry run before it is queued, so a bad entry is refused when it is entered, not when the approver opens it.

finance_requests

A waiting movement is a row of finance_requests: kind, amount_piastres, payload (the movement exactly as it was entered, as JSON), status (pending, approved, rejected, cancelled), the requester, the decider, the time, the decision note and, once approved, the ledger entry it posted. Receipt photos can be attached to a request and follow it.

Request kinds (RequestPayload in controls.ts):

Rules of the lifecycle:

  • One request per key. queueRequest takes an advisory lock on the movement's idempotency key and returns an existing request with the same key while it is pending or approved. A rejected or cancelled request never blocks asking again, so a corrected month's salaries can be sent after a rejection.
  • Checked when entered. The day is checked with eventTime before the request is stored, so a future date fails at once.
  • Never one's own. decideFinanceRequest refuses when the decider is the requester: 403 same_person. Rejecting needs a note (note_required).
  • Claimed once. The decision first runs an updateMany ... where status = 'pending'; if it changed no row, someone else decided first and the answer is request_not_pending. Two approvers clicking at once cannot both post.
  • Posted as entered, by the requester. On approval the stored payload is executed in the same transaction, with the requester as the author of the posting. Every check of the movement runs again then (a bank may no longer hold the money).
  • Cancel by the requester only (not_your_request), while pending. A cancelled or rejected cheque request also cancels its cheque.
  • Audited: finance.request_create, finance.request_approve, finance.request_reject, finance.request_cancel.

Payouts

Payouts to merchants follow the same idea without a request row. A payout is prepared as a draft (one open draft per merchant). From the approval limit, approvePayout must be called by another person than the one who prepared it (same_person), and markPayoutPaid refuses an unapproved large payout with approval_needed. Marking paid also checks that the merchant is still owed at least the payout (payout_more_than_owed) and that the bank holds the money (not_enough_money). Bulk approval approves only payouts at or above the limit (approval_not_needed for the others) and never one's own.

Marking a payout paid by transfer has its own second person control on top of the approval. When the payout is prepared its statement of account (SOA-000001) is frozen; before it is marked paid, the bank slip is uploaded as its proof of transfer (POT-000001) with the amount and reference typed from it, and every active payout check is ticked. assertReadyToPay() in packages/db/src/finance/payout-proof.ts, called by markPayoutPaid, refuses pot_required (no proof), pot_amount_mismatch (the proof's amount is not the payout's), soa_mismatch (no statement, or its net is not the payout's amount), checks_incomplete (an active check not ticked) and 403 same_person when the person marking it paid is the one who ticked the built in check second_person_viewed ("Second person viewed the statement and the proof of transfer"). That check cannot be switched off and can be ticked only once the proof and the statement exist. Replacing the proof of a draft clears every tick; once paid, the proof and the ticks are fixed by a database trigger. A payout paid by cheque uses the cheque register as its proof instead. The full flow is in Merchant money, payouts (chapter 13).

Other two person checks

Several flows have their own form of the rule, each refusing self decisions:

  • Rider withdrawals: a rider never approves their own (own_withdrawal); from the approval limit the payer must not be the approver (same_person).
  • Expense claims: nobody decides their own; from the limit the payer is not the approving manager.
  • Basata deposits: finance never decides a deposit of their own (own_deposit).
  • Purchase orders: approved at once below the limit, otherwise by another person with accounting manage.
  • Petty cash: above finance.petty_cash_limit_piastres (500 EGP) or when the box would keep less than finance.petty_cash_float_piastres (1,000 EGP), the expense waits as a petty_cash request.

Books lock and reopening

The books are closed through a Cairo day (the ledger core chapter explains the table and the trigger). In the API, POST /finance/books-lock needs accounting manage. Moving the date back reopens days: the controller passes the role admin only when the person also has settings manage, and closeBooks then requires a reason of at least five characters. Both directions are audited (finance.books_close, finance.books_reopen) with the old and the new day. The month end checklist and the Close the month run end with this same lock; closing a year sets it through 31 December.

Audit log and History

Every action is audited: who, what, when, before and after.

audit_log rows hold actor_user_id, action, entity_type, entity_id, before and after (JSON) and created_at. The table is append only (trigger audit_log_append_only). Rows are written with recordAudit(tx, ...) in the same transaction as the change, so a change without its audit row cannot exist.

export function recordAudit(tx: Prisma.TransactionClient, entry: AuditEntry) {
  return tx.auditLog.create({
    data: {
      actorUserId: entry.actorUserId,
      action: entry.action,
      entityType: entry.entityType,
      entityId: entry.entityId,
      before: entry.before ?? undefined,
      after: entry.after ?? undefined,
    },
  });
}

Accounting actions are named finance.<what>: for example finance.expense, finance.journal, finance.money_transfer, finance.payout_create, finance.payout_approve, finance.payout_paid, finance.payout_cancel, finance.cash_handover, finance.cash_handover_review, finance.bill_create, finance.bill_payment, finance.cheque_book, finance.credit_note, finance.debit_note, finance.invoice_issue, finance.receipt_attach, finance.account_create, finance.account_update, finance.opening_balances, finance.year_close, finance.month_end_mark, finance.payroll. Contract changes use merchant.contract_*, chatter uses record.note and record.activity.

The History panel of a document page reads GET /history/:entityType/:entityId (apps/api/src/admin/history.controller.ts), newest first, up to 100 rows. Who may read it is decided by RECORD_APPS (packages/shared/src/record-apps.ts): money records (payout, ledger_entry, bill, finance_request, cheque, tax_invoice, rider_withdrawal, petty_cash, expense_claim, basata_deposit, books and others) need accounting view; merchants and riders can be read by their own app or accounting. Record types not listed are for settings manage. A known record must also be inside the person's stores and merchants. The full audit log is browsable in the Settings app at /admin/audit.

Idempotency

Every staff action sends a client generated idempotency key, so double taps and retries apply once. Background jobs are idempotent and safe to run twice.

Idempotency is enforced at three levels:

  1. The ledger: ledger_entries.idempotency_key is unique and post returns the existing entry for a known key (see the ledger core chapter).
  2. Documents: tables created by a person's action (cash handovers, rider withdrawals, Basata deposits, petty cash and others) store the request's idempotency key with a unique index, and the domain function returns the existing row for a repeat. Some movements answer a repeat with the first entry and write one audit row only (deposits, merchant receipts, adjustments).
  3. Requests: queueRequest keeps one pending or approved request per key, under an advisory lock.

Jobs use keys built from the record and the period (a storage day, a month, a deadline day), so a job that runs on two instances at once, or again after a restart, changes nothing.

Error answers

A refusal answers JSON { error: code } with a 4xx status (409 by default, 400 for bad input, 403 for access and same person, 404 for missing records). Some refusals carry plain values beside the code (for example payout_more_than_owed carries amountPiastres and owedPiastres). Input that fails its zod schema answers 400 { error: 'validation_failed', issues }. The web app shows the English or Arabic message for the code from finance.merchants.errors in the messages files, or a generic message for an unknown code.
