Architecture

Shiply Now is one TypeScript monorepo managed with pnpm workspaces. Strict mode is on everywhere. One database (PostgreSQL 16 with PostGIS) holds every record, and one Docker image runs both servers. This chapter describes the layout, the path a request takes, background jobs, deployment and tests, then maps every file that belongs to the accounting system.

Monorepo layout

The dependency direction is strict: shared depends on nothing of ours; db depends on shared; api depends on both; web depends only on shared (its data comes over HTTP). Because business rules live in packages/db, the seed, the demo loader, the API and the background jobs all use exactly the same implementation of each rule.

How a request flows

The /api proxy

The file apps/web/src/app/api/[...path]/route.ts is a route handler that exports the same function for every HTTP method. It rebuilds the target address from API_URL (read at runtime, so one build works on any host), removes hop by hop headers, forwards the body as bytes, and copies the answer back keeping each Set-Cookie header separate. A network failure answers 502 { error: 'api_unreachable' }. A Next.js rewrite is not used because it would freeze the API address at build time.

Middleware

apps/web/src/middleware.ts runs on the Node.js runtime (so the JWT secret is read at runtime and never bundled) for /admin, /store, /rider, /merchant, /finance and /home. It reads the access token's claims and calls decideAccess (apps/web/src/lib/access.ts), which answers allow, send to login, refresh the session first, or redirect to the person's own area. On allow it adds the path in a request header so the app frame can show not found for a page the person may not open.

Authentication

Sign in sets an httpOnly access JWT cookie (HS256) and an opaque refresh token stored hashed and rotated on every use. JwtAuthGuard (apps/api/src/auth/jwt-auth.guard.ts) accepts the token from an Authorization: Bearer header (used by server components) or from the cookie (used through the proxy), verifies it and puts { sub, email, role } on the request. A missing or bad token answers 401 { error: 'unauthenticated' }.

Guards and decorators

The three guards are registered globally in apps/api/src/auth/auth.module.ts with APP_GUARD, so no route can forget them. The decorators in apps/api/src/auth/decorators.ts are:

  • @Public(): skips authentication. Used for routes checked another way (Shopify signatures, Slack signatures, the public tracking page, the website lead form).
  • @Roles(...roles): the route is for these roles only.
  • @Access(app, level?, options?): the route is for team members whose access profile reaches level in app. Without a level, GET and HEAD need view and other methods need use. Options add customerData, salaries, a store or merchant route parameter to check, and further levels in other apps (also). A method decorator overrides the class decorator.
  • @MerchantRight(right): a merchant member needs that right (owners have all); 'owner' limits the route to owners.
  • @CurrentUser() and @CurrentAccess(): parameter decorators that give the handler the claims and the access profile the guard loaded.

Every accounting controller carries @Access('accounting') on the class, and stronger levels on single methods:

@Access('accounting')
@Controller('finance')
export class ControlsController {
  @Post('requests/:id/decide')
  @Access('accounting', 'manage')
  async decide(@Param('id') id: string, @Body(new ZodValidationPipe(decideRequestSchema)) body, @CurrentUser() user) {
    ...
  }
}

A test (apps/api/test/route-access.test.ts) fails when any route has none of @Public, @Access or @Roles, unless it is on an explicit list of routes open to any signed in user.

Domain functions and transactions

A controller does little more than call one domain function with the caller's user id. Domain functions take a Db, which is either the Prisma client or a transaction client, and run their work through inTransaction:

/** Either the full client or the client handed to a $transaction callback. */
export type Db = PrismaClient | Prisma.TransactionClient;

/** Runs fn in a transaction; joins the caller's transaction when db already is one. */
export function inTransaction<T>(db: Db, fn: (tx: Prisma.TransactionClient) => Promise<T>) {
  if ('$transaction' in db) return db.$transaction(fn);
  return fn(db);
}

This lets a delivery, its ledger postings, its order events and its audit rows share one transaction: completeDelivery in orders.ts calls postDeliveryCompleted(tx, ...), which calls post(tx, ...) several times, all inside the same transaction. Either everything is written or nothing is.

Refusals and errors

A business rule refusal throws DomainError(code, status = 409, details?) from packages/db/src/domain-error.ts. The global filter AppErrorFilter (apps/api/src/common/domain-error.filter.ts) turns it into { error: code, ...details } with that status. Validation failures answer 400 { error: 'validation_failed', issues }. HTTP errors keep their usual answer. Anything unexpected answers 500 and raises one server_error admin alert per source and message through ErrorReporter, storing only the method and path, never bodies or query strings.

Background jobs

There is no queue service and no Redis. JobsService (apps/api/src/jobs/jobs.service.ts) starts two timers when the API boots: one every 30 seconds for the business jobs and one every 10 seconds for web push. Each job:

  • opens a transaction and takes a Postgres transaction level advisory lock with pg_try_advisory_xact_lock(<fixed id>); if another API instance holds it, this run does nothing;
  • is idempotent: every ledger posting it makes has an idempotency key (for example storage:<day>:<store>:<merchant>), so running twice changes nothing;
  • remembers in memory the last Cairo day or slot it finished, to skip needless work, but never relies on that memory for correctness;
  • reports a thrown error through ErrorReporter instead of crashing.
const result = await this.prisma.$transaction(async (tx) => {
  const [{ locked }] = await tx.$queryRaw`SELECT pg_try_advisory_xact_lock(${STORAGE_LOCK}) AS locked`;
  if (!locked) return null;
  return chargeStorageDays(tx, now);
}, { timeout: 60_000 });

The accounting jobs are: the daily storage charge (with catch up of missed days), the monthly finance run (recurring expenses prepared as requests, prepayment releases and depreciation, accrual reversals), contract monthly minimum fees and contract payout schedules, the rider cash overdue check every ten minutes, payment reminders to merchants in debit, and the Basata cash deposit deadline. The electronic invoice sync (EtaSync in apps/api/src/finance/eta.ts) has its own one minute timer and sends nothing without its credentials. Merchant emails are sent from an outbox by the same job loop. Jobs can be switched off with JOBS_ENABLED; they are off by default in tests.

Deployment

One Docker image runs everything. deploy/start.mjs:

  1. checks that the database address and the JWT secret are set, and optionally swaps the database name (DATABASE_NAME);
  2. runs deploy/migrations-current.mjs; when every migration folder is already applied it skips prisma migrate deploy (a sleeping free instance wakes faster), otherwise it applies the migrations;
  3. runs deploy/prepare.mjs in a separate process: the one time fresh start when asked, the seed (which only adds missing rows and never overwrites admin edits), and the demo month when DEMO_LOAD is true;
  4. starts the API on 127.0.0.1:API_PORT (inside the container only) and the web app on $PORT (the only public door). If either stops, the container stops so the host restarts it.

One .env file at the repository root serves every app in development; .env.example lists every variable. Secrets are never committed. Backups are the database provider's restore window plus a nightly encrypted dump kept as a CI artifact (see docs/BACKUP.md).
