10. Merchant fees: contracts, prices and the postings of each event

This chapter explains how the system decides what a merchant pays for every delivered order, failed attempt, received unit, stored unit, returned unit and month, and exactly which ledger entries each event writes. Every amount is an integer number of piastres (100 piastres = 1 EGP). Every percentage is an integer number of basis points (bp: 10,000 bp = 100%). No floating point number ever reaches money.

10.1 Conventions used by every fee

The rounding helper

All percentage shares of money in the fee code use one helper, share() in packages/db/src/finance/ledger.ts (identical to bpShare() in packages/shared/src/contracts.ts):

share(amount, bp) = floor((amount * bp + 5000) / 10000)

This is "round half up" to the whole piastre for non negative amounts. Example: 12.5 piastres becomes 13, 12.49 becomes 12.

One entry per fee kind, VAT on each entry

Each fee is its own ledger entry with its own entry kind and its own idempotency key. The VAT of a fee is computed on that fee alone: vat = share(fee, fee.vat_bp). The entry has three lines, built by feeLines() in packages/db/src/finance/postings.ts:

AccountDebitCreditTags
2100 merchant wallet (2100-nnnn)fee + vatstore, merchant, order (when the event has an order)
4101 Delivery and service feesfeesame
2301 VAT payablevatsame

Because VAT is rounded per entry, the VAT of an order can differ by a piastre from 14% of the sum of its fees. A developer rebuilding the system must keep the per entry rounding, because the monthly tax invoice adds up the VAT that was actually booked (chapter 13).

Rules every posting obeys

  • Lines of 0 are dropped by post(). When every line is 0 nothing is written and post() returns null. So a fee of 0 (for example a shipping fee on a contract that has none) leaves no entry at all.
  • The lines of an entry must add up to 0, otherwise post() throws; a deferred database trigger refuses an unbalanced entry as well.
  • The same idempotency key posts once: a repeat returns the first entry. All keys in this chapter are unique per event, so a retried transaction or a job that runs twice changes nothing.
  • Sign convention in the ledger: debit is positive, credit is negative. A merchant wallet is a liability; a credit balance means we owe the merchant, a debit balance means the merchant owes us.
  • Tags: when the caller gives no store or merchant tag, post() takes them from the entry's order, then from the wallets on its lines, then from the rider's store (entryTags() in ledger.ts).

10.4 Resolving a price field by field

resolvePrices(version, tier, standard) resolves each of the nine prices independently:

price[k] = tier[k]  ?? version[k]  ?? standard[k]
           (band)     (contract)     (global setting)

The function used by the postings is contractPricesAt(db, { merchantId, at, orderId? }), which calls pricesForDay(). It returns the resolved prices, the failed delivery rule (10.8), the id of the version (for per product prices), the contract label, the band used (tierFrom) and the order's place in the month (nth).

The all inclusive preset

Most merchants pay one shipping fee that covers everything. The preset allInclusivePrices() (constant ALL_INCLUSIVE_ZERO_KEYS) sets order fixed, order percent, COD, receiving, storage, return and packaging charge to an explicit 0 (null would mean the standard price), clears the fixed failed fee (null) and sets failedDeliveryPercentBp to 10000 (failed attempts cost 100% of the shipment charges).

10.5 Volume tiers

A tier says: "from the nth delivered order of the Cairo month, these prices replace the version's". tierFor(tiers, nth) picks the tier with the highest fromOrder not above nth; before the first band there is none.

The order that crosses into a band and every later order of the month pay the band's prices. Earlier orders are never charged again and never rebated. The count restarts each Cairo month.

How nth is counted

  • For a delivered order: the merchant row is locked (SELECT ... FOR UPDATE) so two deliveries at the same moment count one after the other, then nth = (delivered orders of the merchant with deliveredAt from the start of the Cairo month up to now, this order excluded) + 1.
  • For any other charge (failed delivery, receiving, storage, return): nth is the place the next delivered order would take at that moment, the same count without locking.
  • nth is only computed when the version in force has tiers and its dates cover the day; otherwise no tier applies.
  • Per product prices never take tiers.

Version: order fixed 15 EGP (1,500 piastres), tier from order 501 with fixed fee 10 EGP (1,000). In November the merchant's 500th delivered order pays 1,500 piastres; the 501st and every later November order pay 1,000; on 1 December the count restarts and the first order pays 1,500 again. Orders 1 to 500 are not recharged.

10.7 The delivery posting

When the rider marks an order delivered (packages/db/src/orders.ts), the same database transaction updates the delivery (status, codCollectedPiastres), moves the order to delivered, raises a cod_mismatch alert when the collected cash differs from the expected COD, and calls postDeliveryCompleted() in postings.ts. That function writes these entries in this order:

  1. cod_collected: the cash now belongs to the merchant.
  2. shipping_fee, product_handling, order_fee, cod_fee, packaging_charge (each skipped when 0).
  3. postal_fee: our cost, the postal authority's share of those five fees (see Postal fee below).
  4. rider_bonus: the rider's pay for the delivery.
  5. rider_office_commission, only when the rider is linked to an active rider office (chapter 11).

Postal fee

The postal authority takes fee.postal_bp (default 1000 = 10%) of our fees before VAT on every shipment. It is our cost: it is never charged to the merchant and carries no VAT.

postPostalFee() in packages/db/src/finance/postings.ts runs in the same transaction as the event, right after the fees of that shipment:

delivered order:      base = shippingFee + productHandling + orderFee + codFee + packagingCharge
                      (the five fees just charged on the order, each before VAT)
each charged failed attempt:  base = failedFee (before VAT)
storage, receiving and return fees: no postal fee (they are not shipments)
postal = share(base, fee.postal_bp)          (the same rounding helper as every fee, 10.1)

Idempotency keys: delivery:<deliveryId>:postal_fee for a delivered order and delivery:<deliveryId>:failed_postal_fee for a failed attempt; entry kind postal_fee; memo the order number; data holds the delivery, the base and the rate used. A base or rate of 0 writes nothing (lines of 0 are dropped), and a repeat changes nothing. The setting is global only (no store override), read at the moment of the event.

A delivered order whose fees before VAT add up to 100.00 EGP (10,000 piastres), VAT 14%. The merchant's wallet goes down by 114.00 EGP exactly as without the postal fee (fees 100.00 to 4101, VAT 14.00 to 2301). Separately the postal entry books share(10,000, 1000) = 1,000 piastres: Dr 5103 Postal fees 10.00, Cr 2307 Postal fees owed 10.00. Our income stays 100.00; the postal authority is owed 10.00. In the example of 10.7 (order fee 2,500 and COD fee 550) the postal fee is share(3,050, 1000) = 305 piastres.

Paying: the postal fees owed are paid once a month from Taxes as tax kind postal (payTax() in packages/db/src/finance/payables.ts, TAXES.postal = postal_fee_payable, through submitTaxPayment()): never more than owed (more_than_owed) nor more than the bank or box holds (not_enough_money), the second person rule from the approval limit, and files chosen in the form. The entry is kind tax_payment (Dr 2307, Cr bank or box), memo "Postal fees" and the reference, key tax_payment:<clientKey>. taxesOwed() shows the amount owed as postalPiastres.

Where else it shows: Coming up and due lists it as kind postal (what was owed at the start of the month due at its end, the rest at the end of next month; chapter 15); the four week cash forecast counts it with the taxes in week 0; merchant profit shows it as a cost line of each merchant (lines on 5103 tagged with the merchant, chapter 13); the forecast suggests postal_per_order from the books and budgets the line to 5103 (chapter 15); the journal list puts postal_fee in the deliveries family. It is never part of the VAT report or VAT return, never on an invoice and never on the merchant's statement.

10.8 The failed delivery rule

A failed attempt is charged on every attempt (one entry per delivery row), by postDeliveryFailed() in postings.ts, inside the same transaction as the failure. The rule is failedDeliveryRule(version, tier, resolvedPrices, standardPercentBp) in packages/shared/src/contracts.ts, applied in this order:

  1. A fixed failed fee set on the band or on the version (0 included) is used as it is.
  2. Else the version's failedDeliveryPercentBp, as a share of the shipment charges.
  3. Else, when the resolved shipping fee is above 0, fee.failed_delivery_percent_bp (default 10000) of the shipment charges.
  4. Else the resolved fixed failed fee (the standard fee.failed_delivery_piastres); contracts without a shipping fee behave as before shipping fees existed.

The shipment charges are computed by shipmentCharges():

shipment = shippingFee
         + productHandling(picked units at their product prices)
         + orderFixed
         + share(productsValue, orderPercentBp)
failedFee = (mode fixed)   ? fixedPiastres
          : (mode percent) ? share(shipment, bp)

The COD fee and the packaging charge are never part of the shipment charges (no cash was collected; packaging may be reused). Prices come from contractPricesAt() without an order id, so the band is the one the next delivered order of the month would take.

10.9 Receiving fee

postReceivingFee() runs when staff close an inbound manifest (packages/db/src/inbound.ts), in the closing transaction. Units are all receivedQty of the manifest lines, including extra units and products not listed. Price is receivingPerUnitPiastres of the version in force at the closing moment, at the band of the next delivered order.

fee = sum(line.receivedQty) * receivingPerUnitPiastres
vat = share(fee, fee.vat_bp)

Posting: the standard fee lines (merchant wallet debit, fee income and VAT credit), store tag = the manifest's store. Idempotency key manifest:<manifestId>:receiving_fee; kind receiving_fee.

120 units received at 2 EGP: fee 24,000 piastres, VAT 3,360; merchant debited 27,360 (273.60 EGP).

10.10 Storage, charged daily with catch up

Formula

accrueStorage(db, day, units) in postings.ts charges one Cairo day for every store and merchant pair. Units are every unit of the merchant in every bin of the store at the end of the day, sellable or not (receiving, damaged and held bins included).

daysInMonth = number of days of the calendar month of `day`
fee = floor((units * storagePerUnitMonthPiastres + floor(daysInMonth / 2)) / daysInMonth)
vat = share(fee, fee.vat_bp)
skip the pair when fee <= 0

This is the monthly price divided by the days of the month, rounded half up per store, merchant and day. The prices are those of the version in force on that day at the band the month's deliveries reached (next delivered order). The entry is dated the last millisecond of the day (cairoDayStart(day + 1) − 1 ms), so statements show it on that day.

AccountDebitCreditTags

Idempotency key storage:<YYYY-MM-DD>:<storeId>:<merchantId>; kind storage_fee; data holds day, store, units and monthly price. A day inside closed books is skipped silently (postUnlessClosed() swallows books_closed), never retried.

300 units at 1.50 EGP per unit per month (150 piastres). In November (30 days): floor((45,000 + 15) / 30) = 1,500 piastres per day. In December (31 days): floor((45,000 + 15) / 31) = 1,452 piastres, VAT share(1,452, 1400) = 203.

Units of a past day and the catch up

The free hosting sleeps, so the daily job may run late. chargeStorageDays() in packages/db/src/finance/storage.ts:

  1. finds the last day already done (the newest storage_days row, or before that table existed, the newest day in a storage_fee entry);
  2. charges every day after it up to the last finished Cairo day, at most storage.catch_up_days days (default 7, global; older missed days stay uncharged);
  3. for each day, reads the units of that day from the snapshot table stock_unit_days, or works them out once from the stock and writes the snapshot (first writer wins);
  4. charges the day and writes a storage_days row (also for a day skipped by closed books).

Units of a past day are exact because stock only changes through append only stock movements: unitsAtDayEnds() takes the units held now per store and merchant and undoes every movement (into or out of a bin) made after the end of that day. A negative result counts as 0. The snapshot is written for every merchant, also those paying no storage, because the merchant profit report shares rent by these unit days (chapter 13).

The API job runStorageCharge() (apps/api/src/jobs/jobs.service.ts) runs it under a Postgres advisory lock (pg_try_advisory_xact_lock), at most once per finished day per process.

10.11 Return fee

postReturnFee() runs when staff hand a return parcel to the merchant's collector (packages/db/src/returns.ts). Units are the sum of pickedQty of the return lines.

fee = sum(line.pickedQty) * returnPerUnitPiastres

Standard fee lines; store tag = the return's store. Idempotency key return:<returnId>:return_fee; kind return_fee.

10.12 Monthly minimum fee

A version may set minimumMonthlyFeePiastres. After a month ends, chargeMinimumFees() in contracts.ts (job runContractMinimums(), once per Cairo day, under an advisory lock) tops the month up.

for each day d of the month:
    v = versionInForce(merchant, d)
    if v has a minimum and v's dates cover d: sum += v.minimum; days += 1
minimum = days > 0 ? round(sum / daysInMonth) : 0        (Math.round)
fees    = fee income (4101, before VAT) tagged with the merchant in the month,
          minimum_fee entries excluded (credit notes and adjustments reduce it)
topUp   = minimum − fees;   charge only when topUp > 0
vat     = share(topUp, fee.vat_bp)

A minimum is therefore shared out by days: a contract that starts on the 16th of a 30 day month with a 3,000 EGP minimum gives a minimum of round(15 × 300,000 / 30) = 150,000 piastres. Before charging on the first day after the month, the month's last storage day is charged first (accrueStorage(db, last)), so it counts in the fees. The entry is dated the last millisecond of the month; a month inside closed books is skipped.

10.13 VAT on top

VAT is never part of a contract. It is the single global setting fee.vat_bp read at the moment each fee is booked, added on top of every fee kind (including the minimum top up). Contract screens show it but cannot change it. The VAT credited to 2301 on fees is the output VAT of the VAT report and return (chapter 15).

10.14 Damage compensation and rider charge

Units go to the damaged bin only through a damage report with a cause (arrived_damaged, store_handling, delivery, customer, expired). Admin settles it with settleDamage() in packages/db/src/damage.ts, confirming or changing the cause (a change needs a note). The money moves in the same transaction; settling twice is refused.

companyPays  = cause in ('store_handling', 'delivery')        (COMPANY_CAUSES)
compensation = companyPays ? quantity * product.pricePiastres : 0
riderCharge  = chargeRider ? compensation : 0
               (chargeRider allowed only for cause 'delivery' with a rider on the report)

No VAT: compensation is not a fee.

10.15 Credit limit

assertWithinCreditLimit() refuses a new shipment while the merchant owes us more than the version's creditLimitPiastres (error merchant_over_credit_limit), and raises one merchant_over_credit_limit alert per merchant and Cairo day (key credit_limit:<merchantId>:<day>). No limit set means no check.

10.16 The contract calculator

The contract editor, the sales proposals and the merchant profit what if use pure functions in packages/shared/src/contracts.ts that mirror the postings:

  • orderCharge(terms, standard, vatBp, input): one shipment at its band, every fee and the VAT computed per fee (as booked), plus what the same shipment costs if the attempt fails.
  • monthEstimate(...): orders spread evenly over the month (bands walked from where each starts), storage day by day at the band reached so far (soFar = floor(orders * d / days)), the minimum topping the fees up, VAT on the month total.
  • whatIf(base, params): recomputes shipping, order and COD fees for a booked month, keeps other fees, applies a minimum.
