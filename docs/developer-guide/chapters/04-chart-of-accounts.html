Chart of accounts

Every ledger account has a code taken from its group. The first digit of a code is the account's category; the first four digits are its group. Groups and their rules live in ACCOUNT_GROUPS (packages/shared/src/accounts.ts); the accounts the system itself uses, with their preferred codes and names, live in SYSTEM_ACCOUNTS and DEFAULT_ACCOUNTS (packages/db/src/finance/ledger.ts). The chart was introduced by the migration 20261108090100_chart_of_accounts, which also numbered every account that existed before.

The category of an account is fixed by its type (CATEGORY in ledger.ts). Accumulated depreciation (1701) is an asset account that normally carries a credit balance, so it shows as a negative amount among the assets and reduces the value of equipment.

The codes in this table are the preferred codes. When a preferred code is already taken by another account, the account takes the next free code of its group instead (both in accountId when a system account is first used, and in ensureDefaultAccounts for the default accounts).

A few names stored in an older migration differ from the current code (for example 5101 was first named "Rider delivery bonuses" and is now "Rider pay per delivered order" in SYSTEM_ACCOUNTS). Accounts keep the name they were created with unless finance renames them; the code only gives a name when it creates an account.

System accounts and party wallets

There are three kinds of accounts:

  • System accounts exist once and are found by key (revenue, vat_payable, bank, retained_earnings...). The code posts to them by kind: { account: { type: 'vat_payable' } }. They can be renamed but never closed: their keys are in LOCKED_KEYS in books.ts.
  • Party wallets belong to one merchant, rider, supplier, team member or store. They carry the owner in merchant_id, rider_id, supplier_id, user_id or dark_store_id, have no stored name (they show their owner's name) and can be neither renamed nor closed. isWallet(account) is true for them.
  • Company accounts opened by finance: banks, cash boxes, other assets and liabilities, equity accounts, income and expense categories. Their key is acct:<code>.

A wallet or system account is created the first time a posting names it. The function accountId in ledger.ts looks the key up; when it is missing it chooses the code (the preferred one, or the next free one), and creates the row with upsert so two transactions creating the same wallet at once do not collide:

How codes are numbered

nextAccountCode(tx, group, party) takes the advisory lock ledger_account_code for the transaction, then:

  • for a party group, finds the highest four digit suffix used in that group and adds one: 2100-0001, 2100-0002... It refuses group_full after 9999;
  • for a company group, finds the highest plain numeric code in the group and adds one: 1101, 1102... It refuses group_full after the group's 99th code.
export async function nextAccountCode(tx: Tx, group: number, party: boolean) {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(hashtext('ledger_account_code'))`;
  if (party) {
    const prefix = `${group}-`;
    const rows = await tx.$queryRaw`
      SELECT MAX(CAST(substr(code, 6) AS INTEGER)) AS max FROM ledger_accounts
      WHERE group_code = ${group} AND code LIKE ${prefix + '%'}`;
    const next = (rows[0]?.max ?? 0) + 1;
    if (next > 9999) throw new DomainError('group_full');
    return `${prefix}${String(next).padStart(4, '0')}`;
  }
  const rows = await tx.$queryRaw`
    SELECT MAX(CAST(code AS INTEGER)) AS max FROM ledger_accounts
    WHERE group_code = ${group} AND code ~ '^[0-9]+$'`;
  const next = Math.max(rows[0]?.max ?? group, group) + 1;
  if (next > group + 99) throw new DomainError('group_full');
  return String(next);
}

Store cash boxes are company accounts (not party wallets) of group 1200, so they take plain codes (1201 onward when they were first numbered, the next free code later). Loans call nextAccountCode(tx, 2700, false) when a loan is recorded.

Opening, renaming and closing accounts

createAccount in books.ts (route POST /finance/accounts, accounting use) opens an account in a group whose manualType is set: 1100, 1200, 1400, 2400, 3100, 3200, 4200, 5400 or 5500. Any other group answers group_not_open. The rules:

  • a bank (1100) needs a bank name and an account number (bank_details_required), and the same bank and number cannot be entered twice (bank_account_exists);
  • only a bank may be held in USD or EUR (currency_banks_only);
  • names are unique inside the group in either language (account_name_taken);
  • the code comes from nextAccountCode; the key is acct:<code>;
  • an audit row finance.account_create is written.

updateAccount (PATCH /finance/accounts/:id) renames an account and edits bank details. Wallets cannot be renamed or closed (account_locked). A system account cannot be closed (account_locked). Any other account can be closed only when its balance is zero (account_has_balance). A closed account cannot receive new lines (account_inactive), but its history stays.

Which accounts a journal entry may touch

A free journal entry is the accountant's tool for accruals, reclassifications and compound payments. Because a journal entry could otherwise create or hide money, checkJournalEntry in books.ts limits the accounts it may use. It runs when the entry is entered and again when it is posted (also after a second person approves it).

Other checks of a journal entry: a written reason of at least five characters (reason_required), between two and twenty lines each with either a debit or a credit (invalid_line), debits equal to credits (not_balanced), a day that is not in the future (future_date), and active cost tags. Its idempotency key is journal:<client key>; its kind is journal, or accrual with data.reverseOn set to the first day of the next month, when the daily job posts the reversal (accrual_reversal:<id>).

Opening balances

The balances the books start from are posted once by an owner (accounting manage and settings manage) with recordOpeningBalances. Amounts are typed as an accountant reads them (positive on the account's normal side) and turned into debits and credits with debitNormal; the difference goes to 3301 opening balances. The entry is dated at the very start of the first Cairo day and keyed opening_balance, so a second attempt answers opening_already_posted; corrections are journal entries.
