# Shiply Now

Standalone pilot of Shiply Now: 60 minute delivery for merchants on Shopify, run from small dark stores in Greater Cairo. Stock is placed in a dark store before the customer orders; at order time we only pick, pack and deliver.

This is a standalone system for the pilot. Later it will connect to the main Shiply courier platform (built by Qeema Tech) through APIs and webhooks, so keep every external boundary behind a clean service interface.

## Pilot scope (MVP)

1. Dark stores with delivery zones (polygons) and operating hours
2. Merchant SKU catalog matched to Shopify variants by SKU
3. Stock per dark store and bin: receive, put away, reserve, pick, adjust, count
4. Shopify app: registers one fulfillment service (Shopify Location) per dark store, receives fulfillment requests, reports stock and tracking
5. Storefront zone widget: customer picks area, catalog shows only items in stock at that store, 60 minute option at checkout
6. Order queue per dark store with SLA timers (accepted, picked, out for delivery, delivered)
7. Dark store staff web app (mobile first): receive, pick with barcode scan, pack with photo, hand to rider
8. Rider web app (mobile first): assigned orders, map link, mark delivered with photo or OTP, COD amount collected
9. Admin dashboard: dark stores, zones, merchants, stock, orders, SLA and basic KPIs

Out of scope for the pilot: ML forecasting, virtual stores on third party platforms, WooCommerce, accounting, payouts, Fawry integration, native mobile apps.

Added by the business (Step 11, last): a finance module covering rider cash handover, merchant fees from settings, and merchant statements of COD collected against our fees. It is not full accounting and it never sends payouts by itself; the exact fee model is agreed before the step is built.

## Tech stack

- Language: TypeScript everywhere, strict mode
- Monorepo: pnpm workspaces
  - apps/api: Node.js REST API (NestJS), OpenAPI docs generated
  - apps/web: Next.js app with three areas: /admin, /store (dark store staff), /rider
  - apps/shopify: Shopify app built from the official Shopify app template, GraphQL Admin API only (REST Admin API is legacy, never use it)
  - packages/db: Prisma schema and migrations
  - packages/shared: shared types, zod schemas, constants
- Database: PostgreSQL 16 with PostGIS for zone polygons and point in polygon checks
- Queue and cache: Redis with BullMQ for background jobs (stock sync, SLA checks)
- Local dev: docker compose for Postgres, PostGIS and Redis
- Tests: Vitest for units, Supertest for API, Playwright for key web flows

## Core rules (never break these)

1. Money is stored as integers in piastres. Never floats. Convert to EGP only for display.
2. Stock changes only through stock_movements (append only). on_hand and reserved are derived or updated in the same DB transaction as the movement.
3. Every stock or order state change runs inside a DB transaction. No partial states.
4. Reserve stock at order creation. Release on cancel. Never let available go below zero.
5. Every action is audited: who, what, when, before and after.
6. No hardcoded business values (SLA minutes, capacity, fees, buffers). They live in a settings table editable from admin.
7. All inbound webhooks are verified (Shopify HMAC). All outbound webhooks are signed with HMAC SHA256 and retried with exponential backoff.
8. Background jobs are idempotent (idempotency keys) and safe to run twice.
9. Phone numbers are Egyptian: +20 prefix, 11 digits. All 27 governorates preloaded.
10. UI supports Arabic (RTL) and English (LTR). Strings go through i18n, never hardcoded in components.
11. Never commit secrets. Use .env with a .env.example kept up to date.

## Main entities

dark_stores, zones (PostGIS polygon per dark store), bins, merchants, skus (with shopify_variant_id), stock_levels, stock_movements, inbound_manifests, orders, order_items, order_events (append only), riders, deliveries, settings, audit_log, users with roles (admin, merchant, store_staff, rider, finance), ledger_accounts, ledger_entries and ledger_lines (append only), cash_handovers, payouts.

## Order states

new → accepted → picking → packed → out_for_delivery → delivered
Side states: cancelled, failed, moved_to_standard (when stock is missing or the zone is closed).

## Shopify integration notes

- Use fulfillmentServiceCreate once per dark store with inventoryManagement and trackingSupport on
- Shopify calls callback_url/fulfillment_order_notification for fulfillment and cancellation requests
- Shopify calls callback_url/fetch_stock for stock levels; we also push stock changes through the inventory GraphQL mutations within 60 seconds
- Tracking and delivered status go back through fulfillment mutations
- Storefront widget is a theme app extension (app embed), no theme code edits for merchants

## Decisions log

- Step 1: the earlier Java Swing project lives in legacy/java; the monorepo is at the repo root.
- Step 1: one .env at the repo root for every app. The API and the web app both read it.
- Step 1: auth uses an httpOnly access JWT cookie (HS256) plus an opaque refresh token stored hashed and rotated on use. The web app proxies /api to the API so cookies stay first party. Next.js middleware runs on the Node.js runtime so the JWT secret is read at runtime and never bundled.
- Step 1: locale (en, ar) and theme (system, light, dark) are cookies, so the areas keep plain URLs /admin, /store, /rider.
- Step 1: Egyptian phone numbers accept mobiles only (010, 011, 012, 015) and are stored as +20 followed by 10 digits.
- Step 1: the postgis image's extra extensions (topology, tiger geocoder) are dropped at init; only postgis is used.
- Step 2: stock rules live in packages/db/src/stock (receive, move, reserve, release, pick, adjust) so the seed, the API and jobs share one implementation. Each call is one transaction (or joins the caller's), inserts the movement first, changes levels with guarded UPDATEs and writes audit_log.
- Step 2: stock_levels.on_hand counts only pickable bins. Receiving, damaged and held bins are tracked in bin_stock but are not sellable. Available = on_hand - reserved - stock.buffer_units.
- Step 2: units reserved by orders cannot be adjusted, moved or counted away; such calls fail with would_break_reservations.
- Step 2: the database enforces the hard rules too: CHECK constraints keep stock and money non negative, and triggers make stock_movements, order_events and audit_log reject UPDATE and DELETE.
- Step 2: settings are keyed by (key, scope) where scope is "global" or a dark store id. Definitions and defaults live in packages/shared/src/settings.ts. Defaults: SLA accept 2, pick 10, pack 5, hand over 5, ride 35, promise 60 minutes; stock buffer 0; low stock threshold 5; capacity 20 orders per hour.
- Step 3: GET /coverage (lat/lng, areaId or address), GET /coverage/areas and GET /coverage/search are public. Coverage picks the nearest store whose zone contains the point and that is open (Cairo time, hours may run past midnight) and under its hourly capacity; otherwise it answers outside_zones, at_capacity or store_closed with nextOpenAt.
- Step 3: capacity counts orders placed in the last 60 minutes, excluding cancelled and moved_to_standard, against store.capacity_orders_per_hour (store override, then global).
- Step 3: geocoding sits behind the Geocoder interface (Google today). Without GOOGLE_MAPS_API_KEY address lookups answer 503 geocoding_not_configured.
- Step 3: the admin map uses Leaflet with OpenStreetMap tiles and Geoman for editing; no map API key is needed. A zone that never had an order can be deleted (audited); one with orders answers zone_has_orders and can only be switched off. Zone borders are single polygons inside Egypt, validated by zod and PostGIS ST_IsValid.
- Step 4: merchants have a web area at /merchant (merchant users link to a merchant through users.merchant_id). Merchants create inbound manifests (shipments) there; staff receive against them. Manifest status: expected, receiving, received, cancelled.
- Step 4: receiving puts units in the store's receiving bin (not sellable); put away moves them to a shelf. Extra products not on the manifest get a line with expected 0. Closing a manifest notifies the merchant with expected against received.
- Step 4: stock counts are blind (staff see which products belong in the bin, not how many). Every difference waits for admin approval. If the bin changed between count and approval the count becomes stale and must be redone. Approved differences notify each affected merchant.
- Step 4: merchant notifications are stored in the notifications table and shown in the merchant panel; email or WhatsApp can be added later inside notifyMerchant without changing callers.
- Step 4: every staff action sends a client generated idempotency key, so double taps and retries apply once. Business rule refusals answer JSON { error: code } with 4xx.
- Step 4: scanning accepts typed codes, handheld scanners (keyboard input plus Enter) and the phone camera (@zxing/browser). Phone cameras need https.
- Receiving rules (agreed with the business): goods are received only against an inbound manifest (ASN) that the merchant created first; staff never open one. Once an ASN exists, everything that arrives is received, including products not on it and units above the listed quantity, and the merchant sees them as extra in the summary. Barcodes that are not in the catalog are refused and never enter the system.
- Step 5 rules (agreed, not built yet): when a Shopify order arrives and some items are missing at the store, accept what is in stock, cancel the missing items on the Shopify order, and record it. COD amount is Shopify's outstanding total, in piastres. The 60 minute delivery price is set by the merchant (see Step 6); we record what the order shows. A customer phone that is not a valid Egyptian mobile is accepted, kept as written and flagged for staff. When the store is closed, the Shopify order is still accepted and queued; its 60 minute clock starts at the store's next opening time. When the store is open but at capacity, it is accepted and its clock starts at once, flagged for staff as over capacity. Orders outside every zone of that store are refused so the merchant ships them by standard delivery.
- Step 9: admin date filters take Cairo calendar days (YYYY-MM-DD) and the API turns them into instants with Egypt's summer time (cairoDayStart in packages/shared). Never add a fixed +02:00.
- Step 9: KPIs are computed from orders placed in the range: on time means delivered by the promise time; "were late" counts any order whose stage was ever flagged late; stage times are averages between the stage timestamps. The overview refreshes itself every 20 seconds.
- Step 9: admins manage users (each role needs its link: staff and riders a store, riders a badge, merchants a merchant). Disabling a user or resetting a password signs them out everywhere. An admin cannot disable their own account.
- Step 9: a barcode belongs to one product across all merchants, because the store scans without knowing the merchant. Product files (CSV: sku, barcode, title_en, title_ar, price_egp, weight_grams) are imported all or nothing; prices are converted to piastres without floats.
- Step 9: exports are CSV with a UTF-8 byte order mark so Excel shows Arabic, and cells starting with = + - @ are prefixed with ' so Excel never runs them as formulas.
- Step 9: translation keys never contain dots (next-intl treats dots as nesting); setting names use sla__pick_minutes style keys.
- Step 11 (agreed with the business): merchants pay a fixed fee plus a percentage of the products value per delivered order, a COD fee (share of cash collected), a failed delivery fee, a receiving fee per unit and storage per unit per month (charged daily on all units in stock when the Cairo day closes). The customer's delivery fee stays with the merchant. Every fee is a setting with an optional per merchant value (scope merchant:<id>); VAT on fees is a global setting, 0 until the accountant sets it. Riders are on salary plus a bonus per delivered order (setting, per store).
- Step 11: money is a double entry ledger in piastres. Every entry's lines add up to zero (a deferred database trigger refuses anything else) and ledger rows are append only; corrections are new entries (adjustments need a written reason). Balances are always summed from lines, never stored. Debit is positive; what we owe (merchants, rider bonuses, VAT) and income have credit balances and are shown with the sign flipped.
- Step 11: postings happen in the same transaction as the event: delivery (COD to the merchant, order fee, COD fee, rider bonus), failed delivery, shipment close (receiving). Each has its own idempotency key, so running twice changes nothing.
- Step 11: riders hand cash to their store; staff enter the counted total. Counted cash moves to the store box at once; a difference waits for finance, who write it off or keep it on the rider. Finance records bank deposits from store boxes.
- Step 11: payouts are never automatic. Finance prepares a payout of what is owed up to the end of a Cairo day (one open draft per merchant), transfers it, then marks it paid with the bank reference; only then the ledger moves. Merchants choose daily, twice weekly (Sunday and Wednesday) or weekly (Sunday) schedules. Merchants see their balance, payouts and statements in /merchant/wallet.
- Step 11: the finance role has its own area at /finance (admins can open it too): overview, cash, payouts, merchant wallets and statements, rider wallets and bonus payouts, the journal and a trial balance, with CSV exports. Settings show money in EGP and shares in percent, stored as piastres and basis points.
- Step 5: the Shopify app's server side lives in apps/api/src/shopify behind the ShopifyAdmin interface (HttpShopifyAdmin for real calls, FakeShopify in tests). It uses GraphQL Admin API 2026-10 only. Install is OAuth (authorization code) for a shop that admin first links to a merchant; tokens are stored encrypted (AES 256 GCM, key derived from SHOPIFY_API_SECRET). Shopify's callbacks and webhooks are checked against the raw body HMAC; OAuth returns against the query HMAC and a state cookie.
- Step 5: one fulfillment service (Shopify location) per merchant shop and dark store; its callback address is /api/shopify/fs/<row id>. A notification only triggers a sync; a job every 20 seconds also syncs each shop: outbox first, then pending fulfillment and cancellation requests, then changed stock. Concurrent syncs of one shop share one run.
- Step 5: incoming requests: products are matched by Shopify variant id, then SKU; an unknown product or an address outside the store's zones is rejected so the merchant ships it normally. Otherwise the order is created (units the store lacks are cancelled and later removed from the Shopify order by an order edit) and the request is accepted. Cancellations are granted while the order is still in the store (up to packed), refused once a rider has it.
- Step 5: calls back to Shopify (fulfillment with tracking when the rider leaves, DELIVERED or FAILURE events, item cancellations) are written to shopify_outbox in the same transaction as the order change and retried with growing waits (30 s doubling, up to one hour, 10 tries, then an admin alert).
- Step 5: stock pushed to Shopify is available = on hand minus reserved minus buffer, per location, with inventorySetQuantities (changeFromQuantity null, because we are the source of truth) and an @idempotent key; a product is activated at a location the first time the store holds it.
- Deployment: one Docker image runs the API (127.0.0.1:API_PORT) and the web app ($PORT); deploy/start.mjs applies migrations, seeds when SEED_ON_START=true, then starts both. The web app forwards /api to the API with a route handler that reads API_URL at runtime (a next.config rewrite would freeze the address at build time). Free staging is Render plus Neon, documented in docs/DEPLOY.md.
- Step 7: orders (manual from /merchant and /admin today, Shopify later) go through one intake: coverage picks the store from the delivery point; a closed, full or uncovered area is refused with 409 (outside_zones, store_closed, at_capacity). The order form shows the store status as soon as an area is chosen.
- Step 7: at creation, units the store cannot reserve are cancelled on the order and recorded; if nothing can be reserved the order goes to moved_to_standard. At pick time, Missing cancels the remaining units, releases them, alerts admin and notifies the merchant.
- Step 7: picking is by scan (product, optionally the shelf first). Packing needs a photo; handover is by scanning the rider badge. Riders may carry several orders in one trip up to delivery.max_orders_per_trip, and only if no order would miss its promise.
- Step 7: proof photos are stored in Postgres (photos table, bytea, max 1.5 MB after the phone shrinks them) so the pilot needs no file storage service.
- Step 7: background jobs (SLA late flags) run inside the API every 30 seconds under a Postgres advisory lock instead of BullMQ and Redis; they are idempotent. Redis stays in docker compose for later.
- Step 7: merchants may cancel only new or accepted orders; admin and staff may cancel up to packed. Merchants never see the customer's delivery code.
- Failed deliveries (agreed with the business): a failed attempt goes to attempt_failed while attempts remain (delivery.max_attempts, default 2) and the customer did not refuse; otherwise the order fails for good. "No answer" needs delivery.min_calls_no_answer calls logged from the rider app (default 2) and a door photo; "other" needs a note. The fee and Shopify's FAILURE event happen on every attempt. Staff tap Receive goods back: during attempt_failed the goods stay with the order (no stock change); once failed they go to the held bin. The merchant, staff or admin then retry (goods must be back; the order returns to packed), ship it normally or cancel (both end as failed). Undecided orders fail after delivery.retry_hold_hours (default 48), and goods not back within delivery.return_alert_minutes (default 120) raise one goods_not_returned alert per attempt. Shopify orders are never cancelled by us.
- Step 8: riders deliver with the customer's 4 digit code or a handover photo; COD orders need the cash collected, and a difference raises a cod_mismatch alert. A failed delivery comes back to the store's held bin when staff tap Receive goods back.
- Step 6 (agreed with the business): every checkout check happens before payment. Phase A: our carrier service offers the 60 minute rate only when the origin location Shopify plans is the dark store whose zone holds the address, and that store is open, under capacity and has every item; otherwise only the merchant's next day rates show. Phase B, after the app is approved as an unlisted App Store app: a fulfillment constraints function locks the cart to the widget's store. Merchants buy the plan with carrier calculated rates but never Shopify Plus (Functions in custom apps need Plus, App Store apps do not). The 60 minute price belongs to the merchant: they set it in /merchant, admin can see it but never change it. Production needs an API instance that does not sleep, because Shopify waits only a few seconds for rates.
- Step 6 Phase A (built): POST /shopify/rates/<shop id> is the carrier service callback (raw body HMAC). Each fulfillment service location gets the dark store's address through locationEdit, with address2 "Shiply Now <code>"; a rate request names its origin only by address, so that line tells us the store. The rate code is SN60:<store code>. An empty answer is cached by Shopify for 15 minutes, so when geocoding fails we answer 503 (retried after 30 seconds). Destination addresses are geocoded through the Geocoder and cached in geocode_cache (not found entries expire after a day). The merchant's price is merchants.express_price_piastres (null means off), changed only through PUT /merchant/delivery. Once a shop has a carrier service, fulfillment requests whose shipping line code is not SN60 are rejected (OTHER) so the merchant ships them; a SN60 code for another store raises a shopify_wrong_store alert.
- Step 6 widget (built): a theme app extension (apps/shopify/extensions/zone-widget, app embed, plain JavaScript, no build step) talks to /api/shopify/proxy through the Shopify app proxy (/apps/shiplynow), whose signature (sorted name=value pairs joined with nothing, hex HMAC) is checked on every request. The chosen area is kept in localStorage and on the cart attribute _shiplynow_zone (for Phase B). Availability is a browsing hint only; checkout decides. Widget strings live in its own en and ar tables.

- Tracking: every order has an unguessable tracking_token; /t/<token> is public (no sign in) and shows status, promise time, the delivery code until delivered, COD to prepare, the rider's first name, the live map, the handover photo and a one time 1 to 5 rating. - Returns to the merchant: the merchant asks from /merchant/returns for sellable, damaged or held units of one store. Sellable units are reserved at once; damaged and held units are checked against what open returns already claim. Staff pick by scan in /store/<id>/returns (bin first optional); each unit leaves through a new movement type, dispatch (from a shelf it lowers on_hand and reserved together). The last unit makes it ready; staff hand it over with the collector's name, which charges fee.return_per_unit_piastres and notifies the merchant. Cancelling is allowed only before the first unit is picked and releases the reservations. References are RET-1001 onward per merchant.
- Damage settlement (agreed with the business): units go to the damaged bin only through POST stores/<id>/damage with a cause (arrived_damaged, store_handling, delivery, customer, expired) and, for delivery, an optional rider badge; a plain move with reason damaged answers cause_required. Each report waits in /admin/damage. Admin confirms or changes the cause (a change needs a note). For store_handling and delivery the company credits the merchant quantity × product price (damage_compensation: damage_expense to merchant); for delivery with a rider admin may charge the rider the same amount (damage_rider_charge: the rider owes it as cash). Other causes move no money. The merchant is notified and sees reports under Take stock back; damaged units go back to the merchant through a return.
- Merchant self sign up: /signup is public (POST auth/signup, at most 5 per address in 15 minutes). It creates an inactive merchant with approval pending and an inactive merchant user, and raises a merchant_signup alert. Signing in with the right password then answers 403 account_pending or account_rejected; a wrong password still answers invalid_credentials. Admin approves (opens the merchant and its users) or rejects with a reason in /admin/merchants. Merchants made by admin are approved by default. The merchant home shows an onboarding checklist (products, 60 minute price, Shopify, first shipment) until all are done.
- Hub (agreed with the business): locations are dark stores or hubs (sorting facility), dark_stores.kind. Admin opens either from /admin/stores with default hours and bins (RCV-01, DMG-01, HLD-01, A-01 onward) and can add shelves. A hub takes no orders, has no zones and is never a Shopify location. Once an active hub exists, merchant shipments go only to hubs (shipments_go_to_hub); returns may come from any location.
- Transfers (agreed): only admin creates, approves or cancels them, and they carry no merchant fee. Approval holds the units at the sender (reserve), staff pick by scan (dispatch with transfer_id), Send (units not found are released and raise transfer_short_sent), the receiver scans into receiving (receive with transfer_id) and closes (missing units raise transfer_short_received), then puts away as usual. Store to store always becomes store to hub with final_destination_id; the hub's close creates the onward leg or joins the hub's open onward trip to that store (one trip per store), which is picked straight from the hub's receiving bin without a hold. Cancelling is only possible before picking starts.
- Automatic refill (agreed): every store has a min and max per product (stock_targets, else refill.default_min_units and refill.default_max_units for the store). After refill.run_hour (Cairo) the job prepares the day's drafts once (refill_day): what a store has plus what is already coming is compared with its min; it is filled up to its max from the hub's free stock first, then from other stores' stock above their max (through the hub). One draft per trip; admin approves them (quantities editable) in /admin/transfers. refill.enabled turns it off.
- Area engine (agreed: Greater Cairo): geo_areas holds levels 1 governorate, 2 district (geoBoundaries, CC BY 3.0 IGO, seeded), 3 neighbourhood, 4 compound, 5 street (OpenStreetMap).
